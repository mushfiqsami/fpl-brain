# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The single most important thing

`app.py` is a **generated single-file bundle**, not hand-written source, and as of
this commit **the source that generates it is in this repo** - `fplbrain/`,
`ui.html`, `config.json`, `build_standalone.py`.

Edit the source and run `python build_standalone.py`. Do not hand-edit `app.py`:
the next build silently overwrites it. That is not hypothetical - two sessions
worked on this project at once, one holding only the bundle and hand-editing it,
the other holding the source and regenerating. Eight commits of real work came
within one command of being erased, and had to be recovered by decoding the
base64 blobs back out of `app.py`. The source lives here now so that cannot
recur.

Render only ever runs `app.py`; the source sitting beside it is inert, and the
embedded modules win over the on-disk package because `app.py` registers them in
`sys.modules` before anything imports. Nine Python modules are
base64-encoded into the `_SRC` dict at the top of it and `exec`'d into a synthetic `fplbrain`
package at import time. The UI (HTML/CSS/JS) is base64 in `_UI_B64`, and the preseason player
prior and default config are base64 in `seed.EMBEDDED_PRIOR` / `EMBEDDED_CONFIG`.

The header says "Generated by build_standalone.py — edit the source modules, not this file."
**That build script and the `fplbrain/` source tree are not in this repository.** This repo is the
deployed artifact only (`app.py`, `requirements.txt`, `README.md`, `.gitignore`).

So the edit loop is: **decode → edit the decoded file → re-embed → verify**. Never hand-edit a
base64 blob, and never assume a `fplbrain/` directory exists.

The embedded modules are `api, calibrate, history, model, optimise, report, seed, sim, squad`
(load order is `_ORDER`). Plain-text Python does exist in `app.py` below the blobs — `run_job()`,
`route()`, `load_config()`, `main()`/`serve_cloud()` — and that part is edited directly.

## Commands

Decode the embedded modules and UI into a scratch `decoded/` directory (gitignore it or delete it
when done — it is not part of the repo):

```bash
python -c "
import re, base64, os
src = open('app.py', encoding='utf-8').read()
os.makedirs('decoded', exist_ok=True)
for n, b in re.findall(r'_SRC\[\"(\w+)\"\] = base64\.b64decode\(\s*\"([^\"]+)\"\s*\)\.decode\(\"utf-8\"\)', src):
    open(f'decoded/{n}.py','w',encoding='utf-8').write(base64.b64decode(b).decode('utf-8'))
m = re.search(r'_UI_B64 = \"([^\"]+)\"', src)
open('decoded/ui.html','w',encoding='utf-8').write(base64.b64decode(m.group(1)).decode('utf-8'))
"
```

Re-embed one module (or the UI) after editing it:

```bash
python -c "
import re, base64
mod = 'optimise'                      # module name, or use the _UI_B64 branch below
src = open('app.py', encoding='utf-8').read()
b = base64.b64encode(open(f'decoded/{mod}.py', encoding='utf-8').read().encode()).decode('ascii')
pat = re.compile(r'(_SRC\[\"' + mod + r'\"\] = base64\.b64decode\(\s*\")([^\"]+)(\"\s*\)\.decode\(\"utf-8\"\))')
assert pat.search(src)
open('app.py','w',encoding='utf-8').write(pat.sub(lambda m: m.group(1)+b+m.group(3), src, count=1))
"
# UI instead: pattern is r'(_UI_B64 = \")([^\"]+)(\")' over decoded/ui.html
```

Verify after any re-embed — there is no test suite, so these are the safety net:

```bash
python -c "import py_compile; py_compile.compile('app.py', doraise=True); print('ok')"
# every module still decodes and compiles:
python -c "
import re, base64
src = open('app.py', encoding='utf-8').read()
for n, b in re.findall(r'_SRC\[\"(\w+)\"\] = base64\.b64decode\(\s*\"([^\"]+)\"\s*\)\.decode\(\"utf-8\"\)', src):
    compile(base64.b64decode(b).decode('utf-8'), n, 'exec'); print(n, 'ok')
"
# after a UI change, syntax-check the page JS (a broken blob only fails in the browser):
curl -s http://127.0.0.1:8731/ -o page.html
python -c "
import re; h=open('page.html',encoding='utf-8').read()
open('page_js.js','w',encoding='utf-8').write('\n;\n'.join(re.findall(r'<script[^>]*>(.*?)</script>', h, re.S)))
"
node --check page_js.js
```

Run it (`FPL_NO_GRADIO=1` skips the optional gradio mount, which is not in `requirements.txt`):

```bash
pip install -r requirements.txt      # pulp, openpyxl, fastapi, uvicorn
FPL_NO_GRADIO=1 python app.py        # local: picks a free port from 8731, opens a browser
```

Drive it without the browser — the model runs in a background thread, so poll before reading:

```bash
curl -s localhost:8731/api/status                       # status: running | done, plus a log
curl -s localhost:8731/api/data                         # the whole payload the page renders
curl -s -X POST localhost:8731/api/squad -H 'Content-Type: application/json' -d @squad.json
curl -s -X POST localhost:8731/api/refresh -H 'Content-Type: application/json' -d '{}'
```

**Polling `/api/status` for `"done"` races**: saving a squad or refreshing kicks off a new run while
the previous run's status is still `done`, so a naive poll reads stale data. Wait on the thing you
actually changed, e.g. `until curl -s .../api/data | python -c "...squad_source=='manual'..."; do sleep 3; done`.

There is no lint config, no test suite, and no CI in this repo.

## Architecture

Three model layers feed an integer program. Each layer is in its own embedded module.

**`model.py` — the model.** `TeamStrength` blends a preseason prior with observed xG by empirical
Bayes (`(games·observed + k·prior)/(games + k)`, k = 6 games), then renormalises so the league
averages exactly 1.00. `FixtureModel` turns that into Poisson λ per side with a Dixon–Coles
low-score correction (ρ = −0.035), which matters because clean sheets drive GK/DEF scoring.
`PlayerModel.project()` builds expected points from the actual FPL scoring rules rather than a
regression — appearance, goals, assists, clean sheet, `E[floor(conceded/2)]`, saves, DefCon and
bonus — then applies a per-position calibration multiplier. Per-90 rates are shrunk toward a prior
by minutes (`_shrink`). DefCon and bonus use fitted logistic curves, not Poisson (Poisson broke in
the tails and over-rated high-volume defenders).

**Minutes are the biggest driver and the most bug-prone part.** `raw_start_rate()` → `start_rate()`
→ `minutes_profile()`. Two structural rules live here and are easy to break:

- `calibrate_depth(elements)` shares out each club's `GK_PLACES = 1` and `OUTFIELD_PLACES = 10`
  starting places greedily by start rate. Without it a club projects more starters than it can
  field (measured: ~12 outfielders per club, and three Arsenal keepers all "starting"), and the
  optimiser buys a cheap backup because on the numbers he *is* a starter. **`app.py` must call
  `pm.calibrate_depth(bs["elements"])` right after constructing `PlayerModel`.**
- Preseason, the live element's `minutes`/`starts` are *last season's* totals, earned at the club
  the player is at now — better evidence of role than the archive prior, which blends two seasons
  across two clubs and (via `seed.MIN_MINUTES`) discards exactly the low-minutes seasons that prove
  someone became a backup. `SUB_RATE_GK` (0.02) is deliberately far below `SUB_RATE_OUTFIELD`
  (0.45): keepers are not rotated on.

**`sim.py` — Monte Carlo.** EP is a mean, and captaincy is a convex payoff, so the XI is also
simulated to get p90 / p_haul / p_blank. `captain_value` ranks on `mean + 0.35·(p90 − mean)`, not
mean. The simulation must track the analytic EP; a simulator that silently disagrees with its own
model is worse than none.

**`optimise.py` — integer programs (pulp/CBC).** `build_squad` picks 15 from scratch;
`plan_transfers` decides this week from what you own; `plan_route` makes ownership a *per-gameweek*
decision under real rules (1 FT/week banked to 5, −4 a hit), shortlisted via `max_squad` and
solved under a wall-clock limit. `rank_xi` picks XI/captain/vice/bench order and reports which
constraint it had to drop rather than silently ignoring a preference.

**`squad.py` — your 15.** FPL does not publish picks before the first deadline, so the app stores
its own squad as name + club (element ids are reused across seasons) and `resolve()` matches them
to live players each run. Optional cross-device sync to a private GitHub Gist via `FPL_SYNC_TOKEN`;
every function there is a no-op and must never raise when the token is unset.

**`calibrate.py`** logs predictions, scores a finished gameweek, and nudges per-position
multipliers by only `DAMPING = 0.35` of the measured bias, clamped to `[0.75, 1.30]`, minimum 25
samples — so one freak week cannot wreck the model. **`seed.py`** builds the cold-start player
prior from the vaastav archive (two seasons, recency-weighted) and carries it inside the bundle so
a redeploy needs no network. **`api.py`** wraps the FPL API with a TTL cache under `data/cache/`
and falls back to a stale cache rather than dying mid-gameweek. **`history.py`** diffs successive
runs to surface players the model is changing its mind about.

## Serving

One `route(method, path, body)` function serves both modes. Locally it is behind
`ThreadingHTTPServer`; in cloud mode (`PORT`, `SPACE_ID`, `RENDER` or `FPL_CLOUD` set) it is behind
FastAPI + uvicorn, registered as a **raw Starlette `Route`** — not `@api.get`/`@api.post`, because
`from __future__ import annotations` turns annotations into strings FastAPI cannot resolve, which
produced a 422 on every POST. Gradio is mounted first only so the Space's declared SDK is
satisfied; the real app is the catch-all.

`/sw.js` is a service worker whose cache name is `md5(PAGE)`, so a UI change busts the cache
automatically. `BUILD` (near the top of `app.py`) is displayed in the page header and is the only
way to tell from the browser whether a deploy actually landed — update it when shipping, or a
stale service worker and a failed deploy look identical.

## Conventions worth preserving

- **`plan["out"]` and `plan["inn"]` must stay equal-length and index-aligned**, because the page
  pairs them positionally (`out[i]` with `inn[i]`). Pair like-for-like within a position first,
  then pair leftovers against each other. Ragged lists shift every later row onto the wrong partner
  and render a legal plan as, say, a MID sold for a DEF.
- **One matcher, not two.** The squad editor renders the server's resolution (`squad_resolved`,
  keyed by slot) rather than re-deriving matches in JavaScript. A second client-side matcher scores
  differently and cannot know which players other rows have taken, so it could tick one player
  while the model scored another.
- `resolve()` scores candidates on name and club alone; whether the best one is already taken is a
  *separate* question. Folding a "taken" penalty into the score let a fragment match win and put a
  player nobody typed into the squad.
- `data/` is gitignored and ephemeral on hosted boxes (squads, cache, prior, calibration,
  history). Nothing may depend on it existing; that is why the prior and config are embedded.
- The comments in this codebase explain *why*, usually citing the bug that motivated the code.
  Match that when editing — and when a comment explains a trap, check you are not reintroducing it.

## Measured findings — do not re-derive these from intuition

Each was tested, and several contradicted the assumption they were built to
confirm. Re-measure before overturning any of them; do not re-argue them.

**The model ranks players far better than it times them.** 2025/26, 301 players
with 8+ scored gameweeks: projection-vs-result correlation is **+0.713 across**
players and **+0.159 within** a player across his own gameweeks. So two players
on the same season mean are worth the same in total points whatever the shape of
their returns, and capturing a peak needs timing the model does not have. Pick on
season-long quality; do not rotate chasing form. Spikiness also tracks ability —
in a 3-6 ppg band the spikiest third averaged 4.25 against the steadiest third's
3.55 — so any steady-versus-explosive comparison that does not hold the mean
fixed is measuring how good the players are, not the shape of their scoring.

**Chasing ceiling through squad selection does not work.** 20,000 joint
simulations per setting: protect (0.20 ceiling appetite) returns 66.43 mean at
15.21 sd; chase (0.70) returns 65.36 at 15.24. Chase costs 1.07 points a
gameweek (se 0.15) and buys 0.03 of standard deviation. Eleven roughly
independent scores summed together concentrate, so one player's fat tail is
averaged away by the other ten — team variance is set by how many players there
are, not how spiky each is. A lower appetite therefore wins at *every* target:
protect reaches 2538 8.8% of the time against chase's 5.1%. Ceiling belongs on
the captain, one score doubled with nothing to average it away. An earlier
6,000-iteration run said the opposite and was noise.

**Transfer cadence is unpriced.** Spending every 1, 2, 3, 4 or 5 gameweeks
differed by 2.4 points across GW1-12 — noise. That is not evidence cadence does
not matter, but that the model cannot see it: projections are treated as
certain, so waiting buys nothing, when the real reason to bank is optionality
against news that has not happened yet.

**Autosubs are worth less than they feel.** With a near-nailed XI a substitution
fires about 0.13 times a week, and a £27m bench produced the same
10th-percentile week as a £17m one. Pay for a bench for Bench Boost and for
mid-season injuries the snapshot cannot see, not for weekly rescues.

**The simulator is calmer than football.** A joint simulation of a real XI puts
gameweek sd near 15.2; measured against actual results it is 21.2. Season
forecasting uses the measured figure — the wider, more pessimistic one.

**What the system actually delivers.** `season_test.py`, walk-forward on
2025/26, building the best legal £100m squad from what was knowable before each
gameweek and scoring it on real results including blanks: **61.8 actual against
67.5 projected**, over 16 gameweeks. The 5.7 shortfall is NOT applied as a
correction — its 95% interval is -18.0 to +6.6 and cannot be told apart from
zero. 61.8 a gameweek is 2,349 over a season.

**Context for any target.** 2025/26 was won with **2538**. A target above that is
not ambitious, it is beyond what the best of ten million entrants managed.
